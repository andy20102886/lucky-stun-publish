# 深水区排错

## 一、Lucky 侧接口（脚本内部用，排错时也手敲）

**签名规则**（每个请求都要）：

- 取毫秒级时间戳，**去掉末 12 位**，得到一个 1~2 位的数 `A`；
- 把 `A` 的各位数字求和，再 **% 8**，得 `B`；
- query 加 `?_=<A><B>`；再加请求头 `Lucky-Admin-Token: <口令登录后拿到的 token>`。

关键接口：

```
POST   /api/stunrule                                   建规则（body = 完整规则对象，建议先克隆一条现有规则再改）
DELETE /api/stunrule?key=<key>                          删规则
GET    /api/stunrulelist                                规则 + 当前公网地址
GET    /api/stun/<key>                                  单条完整字段
GET    /api/stunrule/enable?key=&enable=false|true       重启打洞（＝界面上的「禁用 → 启用」）
POST   /api/cron/list                                   计划任务 CRUD（守护脚本靠它挂定时）
```

> 「建规则」不要凭记忆手拼字段：**先 GET 一条现有规则当模板，改掉目标 IP/端口和名字再 POST**，能避开大半字段坑。

## 二、为什么打洞会失败

按出现概率排序：

1. **目标服务没在监听。** 通道能建起来，但打开是死路。先在内网 `curl <IP>:<端口>` 确认有响应。
2. **内网机默认路由不对，被本地代理/旁路由劫持。** 典型症状：穿透探测拿回来的「公网地址」落在**代理/CDN 的网段**（而不是运营商网段），于是四条通道全废、早上起来全部掉线。
   - 自查：`nslookup <任意域名>` 若返回 `198.18.x.x` 这类假地址 → 说明 DNS 被 tun 模式代理接管了；
   - 再查出口：`curl -s https://api.ipify.org`，若不是运营商 IP 而是 CDN 网段，问题就在这里；
   - 处置：把默认路由指回真正的出口路由器（注意有些设备 DHCP 会覆盖你手写的网关，要在 DHCP 侧固定）。
3. **运营商 NAT 类型变了 / 时好时坏。** 重试一次，或换个时间段。

## 三、守护脚本（自愈）设计要点

挂在内网机上，每 5 分钟跑一次，逻辑就四步：

1. **纳管**：拉 `stunrulelist`，发现本地没有对应监控的新规则 → 自动给它在 UptimeRobot 建一个 `STUN-<规则名>` 的 Port-TCP 监控；
2. **同步**：规则当前 `IP:端口` 与监控目标不一致（端口漂了）→ 更新监控目标；
3. **自愈**：监控判 DOWN → 调 `enable=false` 再 `enable=true` 重新打洞；
4. **刹车**：UptimeRobot 免费版上限 50 个监控，**到 45 就停手**，别把额度打爆。

挂在 Lucky 的计划任务里最省事（Lucky 常驻，不用另开系统定时器）。

## 四、常见误判

| 看起来像 | 其实是 |
|---|---|
| 「通道是通的，说明服务没问题」 | TCP 探测由穿透点在本地应答，**通了不代表后端服务活着** |
| 「端口每次都变，是不是坏了」 | 正常。穿透端口**本身就无法指定/固定**，所以对外永久只发固定入口链接 |
| 「平台面板少一条规则」 | 平台只在**收到过地址推送**后才有记录；地址没变过就不会推。手动 `publish` 会主动推一次 |
| 「访问面板口令报错」 | 口令可能是残缺的提醒/误记。以本机配置文件里的值为准 |

## 五、日志怎么读

- 发布脚本每步都打 `[n/5]`，卡在第 2 步（等打洞）= 没拿到公网地址，看 §二。
- 拿到地址但访问报错 → 看 §四第一行（后端服务）。
- Cloudflare 报 `1010` → UA 被拦，脚本已伪装浏览器，自己写脚本记得带 `User-Agent`。
